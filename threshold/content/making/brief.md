# tracé 제작기: 인스타그램 콘텐츠 작업 지시서

이 문서는 다른 Claude Code 세션에 넘기는 자료입니다. 유혜원이 Claude Code와 함께 산책 지도 서비스 **tracé**를 만든 과정을 인스타그램 콘텐츠로 만들려고 합니다.

콘텐츠는 세 덩어리로 짭니다.

1. **전**: 내가 어떤 사람인지 탐구하고, 무엇을 하고 싶은지 욕구를 기록
2. **과정**: 그래서 어떤 과정 속에서 무엇을 했는지 기록
3. **후**: 그 과정이 어떤 결과로 이어지고 있는지, 지금 진행 중인(ing) 기록

아래 내용은 실제 작업 대화와 커밋 기록에서 뽑은 **사실**입니다. 사용자가 한 말은 따옴표 안에 원문 그대로 옮겼습니다(오타 포함). 콘텐츠에서는 맞춤법만 다듬어 쓰세요.

함께 넘기는 파일: `tracé-portfolio-images.zip` (앱 화면 15장, 6장 참고).

## 0. 지켜야 할 것

- **지어내지 마세요.** 이 문서에 없는 감정, 동기, 깨달음, 수치를 만들지 마세요. `[본인 확인]` 표시는 사용자에게 물어서 채울 자리입니다.
- **"후" 파트에 수치를 쓰지 마세요.** 사용자 수, 만족도, 방문 수 같은 데이터는 아직 없습니다(10월 30일 기준). 설문과 통계는 준비만 됐습니다.
- **AI 표기**: Claude Code와 함께 만든 것은 숨기지 않는 게 이 이야기의 핵심입니다. 다만 어떤 말로 표현할지는 사용자가 정합니다. 사용자가 한 일(기획, 판단, 방향, 레퍼런스 선정, 사진 촬영, 실사용 테스트)과 Claude가 한 일(코드 구현, 버그 수정, 배포 설정)을 섞지 마세요.
- **레퍼런스 이미지 금지**: 사용자가 참고한 남의 작품 이미지(잉크 선 관계도, 사진 그리드 보드 등)는 싣지 마세요. 말로만 설명하세요.
- **사진 확인**: 앱 화면에 나오는 도쿄 사진 4장은 사용자가 직접 찍은 것입니다. 간판과 사람이 보이니 공개해도 되는지 확인하세요.
- **샘플 표시**: 앱 속 구역 설명은 "[샘플]" 자리표시입니다. 실제 여행자의 추천처럼 소개하지 마세요.
- **저장소는 비공개**입니다. 코드 링크를 걸지 말고 배포 링크만 쓰세요: https://trace-threshold.vercel.app

## 1. 한눈에 보기

- **무엇**: 도쿄 여행 중 우연한 산책을 위한 지도 서비스. 다른 여행자가 "산책 구역"(중심과 반경만 있고 정해진 경로는 없는 영역)을 추천하면, 방문자는 길 안내 없이 그 구역을 직접 헤맨다. 걸은 길과 남긴 기록이 곧 "나의 지도"가 된다.
- **이름**: tracé. 프랑스어로 '그려진 선, 자취'.
- **한 문장 컨셉** (사용자 원문): "지도를 굳이 api 안쓰고 내가 돌아다닌 헤멘 곳이 곧 길이고 나의 지도다"
- **기간**: 2026년 10월 4일 ~ 진행 중. 실제로 작업한 날은 10/4, 10/6, 10/7, 10/21, 10/24, 10/28.
- **규모**: 저장소에서 PR 16개, 작업 커밋 33개(머지 제외).
- **도구**: Claude Code(구현), GitHub, Vercel(배포), Figma(초기 디자인), Google Drive와 Google Forms(설문). 사용자는 코드를 직접 쓰지 않고 대화로 방향을 지시했습니다. `[본인 확인: 이렇게 표현해도 되는지]`

## 2. 전: 나는 누구이고, 무엇을 하고 싶었나

### 대화와 문서에서 확인된 사실
- 사용자는 **여행 서비스를 운영**하고 있다. 그 서비스에서 데이터 기반 추천이 "늘 인기있고 비슷한 장소만" 추천하는 것을 봤다. `[본인 확인: 서비스 이름과 역할을 공개해도 되는지]`
- 그래서 **서울의 극심한 장소 편향**을 연구했다. 연구에서 던진 질문은 두 가지다(원문).
  - "알고리즘이 편리하지만, 동시에 우리의 선택을 제한한다면?"
  - "인기있는 선택이 정말 나를 위한 선택이라고 볼 수 있을지?"
- 연구에서 나온 사용자 반응(원문): 새 장소를 추천받아도 신뢰가 없으면 결국 "평점 높은 익숙한 장소로 돌아간다".
- 연구의 결론: 편향은 없애야 할 결함이 아니라 **해석할 수 있는 정보**로 바꿔야 한다. UX는 중립적 도구가 아니라 해석의 장치다.
- 사용자는 Claude Code를 쓰기 전에 이미 **기획 문서 묶음**을 써 두었다: 제품 원칙(AGENTS.md), PRD, 사용자 흐름, 용어 체계, 시각 체계, 인터랙션 원칙, 데이터 모델, API 계약. 첫 요청은 이 문서들을 올리고 "이걸로 MVP 만들기 실행"이었다.
- 제품 원칙에 쓴 것: 알고리즘의 권위보다 사람의 관찰, 추천보다 사용자의 주도, 참여 최적화보다 편집적 의미, 장소는 좌표가 아니라 살아 있는 맥락. 인기 순위, '최고의 장소' 라벨, 무한 피드, 불투명한 AI 추천은 일부러 넣지 않는다.
- 같은 날 **두 번째 버전**도 원했다(원문): "이건 도시산책자를 위한 서비스이고 다른 버전은 동일한 컨셉이지만 커리어의 지도임 / 헤메는 중임을 드러내되, 내가 최근 클로드 코드로 만든 [돌아보는 길] 설문과 컨셉을 참고하면 됨"
  - 즉 **"헤매는 중"**은 도시 산책만이 아니라 사용자 자신의 커리어에도 겹쳐 있던 주제다. `[본인 확인: 이 연결을 콘텐츠에서 드러내도 되는지]`
- 이전에도 Claude Code로 "돌아보는 길"이라는 회고 설문을 만든 적이 있다. 관련 사이트 "The Principles of Tracé"(공간에서 배운 16개의 원칙을 모은 에세이)도 있다: https://trace-user-experience.vercel.app

### 사용자에게 물어서 채울 것 `[본인 확인]`
"전" 파트는 이 질문들의 답이 있어야 진짜 이야기가 됩니다. 추측해서 쓰지 마세요.
1. 이 프로젝트를 시작할 때 나는 어떤 시기를 지나고 있었나? ("헤매는 중"이라는 말이 어디서 나왔나)
2. 왜 연구로 끝내지 않고 직접 만들어 보고 싶었나?
3. 코드를 못 쓰는(또는 안 쓰는) 기획자로서 직접 만든다는 것에 대해 어떤 마음이었나?
4. 산책이나 헤매는 경험이 나에게 개인적으로 어떤 의미인가?
5. 왜 서울이 아니라 도쿄였나? (대화에는 결정만 있고 이유가 없음)
6. 이 프로젝트로 얻고 싶었던 것: 포트폴리오, 실제 서비스, 나에 대한 탐구 중 무엇이었나?

## 3. 과정: 무엇을 했고, 어디서 넘어졌나

각 장면은 **상황 → 시행착오 → 판단**의 순서입니다. "콘텐츠 포인트"는 슬라이드 한 장으로 쓸 만한 문장입니다.

### 장면 1. 문서로 MVP 만들기, 그리고 첫날의 삽질 (10/4)
- 상황: 미리 써 둔 기획 문서를 Claude Code에 올리고 "이걸로 MVP 만들기 실행".
- 시행착오
  - **엉뚱한 저장소**: 작업이 처음엔 블로그용 저장소(`blog-starter-kit`)에 올라갔다. 사용자 원문: "뭔가 제대로 안된거 같음 깃허브 푸시가". 그래서 `trace` 저장소를 새로 만들고("만들었어 trace") 옮겼다.
  - GitHub와 Vercel에 익숙하지 않아 같은 질문을 여러 번 했다: "깃허브에서 pr 병합 해도 됨?", "된건가", "이렇게 하는 거 맞나", "왜 병합햇는데 링크에 반영안되지".
  - 회고 설문 사이트와 분리해서 배포하는 방법을 물어, 한 저장소에서 Vercel 프로젝트 두 개(도시판, 커리어판)로 나눴다.
- 사용자 원문 감상: "너 코덱스보다 편하다"
- 콘텐츠 포인트: "코드를 몰라도 만들 수 있다. 하지만 '푸시', '병합', '배포'라는 말부터 배워야 했다."

### 장면 2. Figma와 맞추기, 그리고 다크 테마의 실패 (10/4)
- 상황: Figma 디자인 파일을 연결해 화면을 맞췄다.
- 시행착오
  - 사용자 원문: "뭔가 디자인이랑 레이아웃이랑 안맞는 거 같은데"
  - Figma 무료 플랜의 호출 제한에 걸려 디자인을 끝까지 읽어 오지 못했다.
  - 사용자가 다른 곳에서 배운 방법을 가져왔다(원문 요약): 스크린샷을 첨부하고 "색상, 폰트, 모서리, 그림자, 간격을 토큰으로 먼저 추출해서 파일로 만들어"라고 시킨 뒤, 그 토큰만 쓰게 하기. → 디자인 토큰 체계의 시작.
  - 다크 테마를 입혔다가, 같은 날 도쿄 컨셉으로 바꾸면서 "디자인 컬러만 원래대로 돌려줘".
- 콘텐츠 포인트: "AI에게 '예쁘게'라고 말하면 안 된다. 색, 폰트, 간격을 숫자로 먼저 정해야 했다."

### 장면 3. 여권 도장 마커와 "텍스트 간 여백" (10/4)
- 상황: 도시 산책자에 어울리게 지도 마커를 여권 도장 모양으로 만들었다(원문: "지도 마커를 도시 산책자에 맞데 레퍼런스 처럼 도장으로 해줘").
- 시행착오
  - 도장 글씨가 잘렸다: "도장 짤리니까 글씨 줄이고 도장 안에 톤텐츠는 영어로"
  - 여백 요청을 세 번 했다: "여백 전체적으로 정리해줘", "텍스트 간 여백 필요해", "텍스트 간 여백 좀"
  - 이 도장 마커는 이틀 뒤 전부 사라진다(장면 5).
- 이미지: `v1-stamp-map.jpg`
- 콘텐츠 포인트: "공들인 도장은 이틀 만에 버렸다. 예쁜 것과 맞는 것은 달랐다." `[본인 확인: 버린 이유를 이렇게 말해도 되는지]`

### 장면 4. 서울에서 도쿄 여행으로 (10/4)
- 사용자 원문: "도쿄 여행을 컨셉으로 잡을게 그래서 여행중 우연한 산책이 가능한 구조 도쿄 여행자가 산책 구역(데리브)를 추천해주고 사용자가 직접 탐험 하는 것임"
- 의미: 연구는 서울에서 출발했지만, 프로토타입의 무대는 **여행 중 낯선 도시**로 바뀌었다. 장소를 고르는 서비스가 아니라 **구역을 건네고 헤매게 하는** 서비스가 됐다.
- `[본인 확인: 왜 도쿄였는지]`

### 장면 5. 레퍼런스 4장과 컨셉의 발견 (10/6)
- 상황: 사용자가 레퍼런스 보드 4장을 골라 아주 구체적으로 지시했다(원문 일부): "타일 레이어 제거, 행정경계 GeoJSON만 opacity 0.15 / 마커는 검은 원 … / 같은 날 기록은 시간순으로 … 곡선 연결 / 완성 후 레퍼런스와 스크린샷 비교해서 다른 점 3개 찾고 고쳐."
  - 색은 종이색, 잉크색, 빨강 하나만. 빨강은 **한 곳에만** 쓴다. 모서리 0, 그림자·그라디언트·이모지 없음.
- **전환점**: 결과물을 보고 사용자가 컨셉을 다시 말했다. "우리 컨셉 이게 좋은 거 같음 지도를 굳이 api 안쓰고 내가 돌아다닌 헤멘 곳이 곧 길이고 나의 지도다"
  - 지도 API(구글 지도 같은 바탕 지도)를 쓰지 않는다. 바탕은 비어 있고, 내가 걸은 선과 남긴 기록만 지도가 된다.
- 이미지: `v2-ink-map.jpg` → `v3-mine-empty.jpg`(아직 걸은 곳이 없는 빈 지도) → `v3-mine-walked.jpg`(걸은 길이 곡선으로 남음)
- 콘텐츠 포인트: "지도 API를 버리자 컨셉이 보였다. 빈 종이에서 시작하는 지도."

### 장면 6. 만들고, 빼고, 또 뺐다 (10/6)
결정이 몇 분 간격으로 바뀌었다. 바뀐 순서 그대로가 이야기다.
1. Claude가 "다른 여행자가 추천한 구역은 지도에서 빼고, 구역 카드와 목록에서만 보여요"라고 제안. 사용자: "이건 필요해 / 나머진 다 좋어"
2. 바로 다시 판단: "이것보다 지도에서 큐레이션 지도, 나의지도가 나뉘는 게 좋을 거 같음 큐레이션 지도는 기존처럼 보이고" → 한 화면 안의 토글(`v3-curated-mine-toggle.jpg`)
3. 아카이브의 관계 그래프 탭: "뭔가 겹치는 내용같아 빼도 될듯" → 삭제(`v2-archive-graph.jpg`는 이제 없는 화면)
4. 탭 구조를 통째로 다시: "나의 지도는 MY 탭에 나오면 될듯 지도뷰로 / Walk:는 가운데 강조 버튼으로 / map(탐색 큐레이션 지도만) / 아카이브 랑 MY를 합쳐서" → MAP | **WALK** | MY
5. "MY에 지도뷰가 디폴트"
6. 무작위로 구역을 뽑아 주는 "Drift by chance" 기능: "랜덤뽑기는 빼줘" `[본인 확인: 뺀 이유. 예를 들어 '우연도 시스템이 고르면 또 하나의 추천'이라는 생각이었는지]`
- 콘텐츠 포인트: "이날 가장 많이 한 일은 만드는 것이 아니라 빼는 것이었다."

### 장면 7. 직접 써 보니 보인 버그들 (10/6~10/7)
사용자가 배포된 앱을 직접 써 보며 찾은 문제들이다.
- "왜기록햇는데 MY에 지도애 안남지 아카이브는 잇음" → 기록이 그리드에는 있는데 나의 지도에는 안 보였다. 수정.
- "위치 허용 기능이 안됨" → 웹에서 위치 권한이 제대로 동작하지 않았다. 수정하고, 실패하면 이유를 화면에 알려 주게 함.
- "위치 / 좌표 없어도 내 지도 는 어차피 행정 구역 없으니까 기록에 남게" → 위치 없이 남긴 기록도 나의 지도에 시간순으로 놓기. 버그를 고치다 컨셉이 더 선명해진 장면.
- "큐레이션 지도 영역이 다 뭉쳐져서 안보임" → 지도를 화면보다 크게 펼치고 손가락으로 끌어 돌아보게 함("상하 좌우로 스와이프 스크롤 하며 보는 구조 지도처럼").
- **늦게 발견한 실패**: 10/28 포트폴리오 화면을 찍다가, 웹에서 **산책 경로가 아예 기록되지 않는** 버그를 찾았다. 10/6 위치 권한을 고치면서 생긴 문제로, 약 3주 동안 배포된 상태였다. 수정했다.
- 콘텐츠 포인트: "AI가 만든 앱의 버그는 결국 내가 걸어 봐야 보였다."

### 장면 8. "이 길로 걷기"와 경로를 보여주지 않는 결정 (10/6)
- 상황: 다른 사람의 기록을 보고 그 자리에 가고 싶을 때 쓰는 "이 길로 걷기" 버튼을 추가했다.
- 사용자의 고민(원문): "근데 이길로 걷기 하면 어쨋든 구역과 거리는 알아야되잖아 어떤 경로로 움직였는지 그런건 우리 데이터 상에 기록 텍스트랑 이미지로 알수 있나 아님 그냥 시작점만 보여줄가"
- 판단: 구역과 지금 위치에서의 거리, 걸어서 걸리는 시간은 보여 준다. **다른 사람이 걸은 경로는 보여 주지 않고 시작점만.** 경로를 공개하면 동선과 집이 드러날 수 있고, 정해진 길 없이 헤맨다는 컨셉과도 어긋난다. 사용자 답: "고"
- 길 안내는 앱이 하지 않고 구글·네이버·카카오 지도로 넘긴다.
- 이미지: `now-02-record-sheet.jpg`, `now-03-handoff.jpg`
- 콘텐츠 포인트: "보여줄 수 있는 것과 보여줘야 하는 것은 다르다."

### 장면 9. 내 사진, 살아 있는 점 (10/6)

### 사용자가 AI와 일한 방식 (관찰)
콘텐츠에 쓸 수 있는 "일하는 법" 소재입니다.
- 짧은 한국어 한 줄로 방향을 정했다: "푸시!", "고", "MY에 지도뷰가 디폴트".
- 말로 설명하기 어려운 것은 **스크린샷과 레퍼런스 이미지**로 보여 줬다.
- 결과물을 보고 **바로 빼는 결정**을 많이 했다(그래프 탭, 무작위 뽑기, 커리어판).
- 레퍼런스를 줄 때 **숫자로** 줬다(색 코드, 투명도 0.15, 원 크기 6~14px).
- 마지막에 "레퍼런스와 비교해서 다른 점 3개 찾고 고쳐"처럼 **검토까지 시켰다**.
- 버그는 직접 써 보며 찾았고, 증상을 자기 말로 전했다.

## 7. 콘텐츠 구성 제안 (사용자와 정한 뒤 진행)

### 먼저 사용자에게 물을 것
1. 계정 성격: 개인 기록 계정인지, 커리어나 포트폴리오 계정인지. 말투(반말 일기체 / 존댓말)는?
2. 형식: 캐러셀 3편(전·과정·후)인지, 장면별 연재인지, 릴스도 하는지.
3. 2장의 `[본인 확인]` 질문 6개에 대한 답.
4. AI 사용을 어떤 말로 표현할지.
5. 여행 서비스 이름, 도쿄 사진 공개 여부.

### 3편 캐러셀 예시 뼈대 (문구는 사용자 답을 받은 뒤 쓰기)
- **1편 · 전** (6~8장): 운영하던 여행 서비스에서 본 것 → 연구 질문 두 개 → "평점 높은 익숙한 장소로 돌아간다" → 나는 지금 헤매는 중 `[본인 확인]` → 그래서 만들어 보기로 했다 → 미리 써 둔 기획 문서들
- **2편 · 과정** (8~10장): 첫날의 삽질(장면 1~2) → 공들인 도장을 버림(3) → 지도 API를 버리자 보인 컨셉(5) → 빼고 또 뺀 날(6) → 걸어 봐야 보인 버그(7) → 경로를 보여주지 않는 결정(8) → 시행착오 모음 한 장
